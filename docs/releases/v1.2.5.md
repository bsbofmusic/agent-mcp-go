# AMG v1.2.5

## Background

Two things were missing rather than broken. A deployment had no way to ask a binary what version it is: `agent-mcp-go --version` exited 2 because the flag did not exist, so a verification could only guess the on-disk version from an MCP `initialize` handshake — which reports the *running* process, not the file that the profile and `ExecStart` will use next. And the operations docs still described AMG as being upgraded by `tg`, which stopped being true: AMG is not in TG's version upgrade scope, and the published v1.2.4 rollback generation number was stale.

The four v1.2.4 fixes shipped without a live acceptance pass on this deployment. This round carries that pass.

Runtime capabilities, the 40-tool catalogue, and the configuration surface are unchanged. No new daemon, cache layer, second registry, dependency, or command-line dependency is added.

## Changes

- **`agent-mcp-go --version` prints one line and exits 0.** The output is `agent-mcp-go 1.2.5`, formatted by a small `versionString()` helper that reads the existing `version` constant — the same constant the MCP `serverInfo` handshake and the startup log use, so there is no second version source that can drift. The flag is handled immediately after `flag.Parse()` and **before** the `*path == ""` config check, so no `--config` and no `AGENT_MCP_GO_CONFIG` is needed. `-version` is accepted because Go's `flag` package treats one and two leading dashes the same. Nothing else about flags changed: `-config` keeps its name, default, and usage string, and a missing config still fails with the same message and exit code.
- **The two probes prove different things, and both are documented.** `agent-mcp-go --version` proves which binary is on disk and activated; `initialize.serverInfo.version` proves which version the running process is. A restart that did not take, or a `/proc/<MainPID>/exe` that ends in ` (deleted)`, shows up as a disagreement between them instead of a false pass. Check both after a deploy:

  ```sh
  agent-mcp-go --version                     # expect: agent-mcp-go 1.2.5
  systemctl --user show -p MainPID --value agent-mcp-go.service
  readlink "/proc/<MainPID>/exe"             # must not end in " (deleted)"
  # then initialize over /mcp and read result.serverInfo.version
  ```
- **AMG is documented as outside TG's version upgrade scope.** The `agent-cli` profile membership is unchanged — AMG is still installed in `/home/agent/.local/state/nix/profiles/agent-cli` and still runs as `agent-mcp-go.service` — but the update path is AMG's own direct release flow: GitHub Release tarball → manual `version` + SRI `hash` pin in `host-infra/packages/agent-mcp-go.nix` → `nix build --no-write-lock-file .#agent-cli-store` in an independent unit → `nix profile upgrade --profile … --all --impure` → `systemctl --user restart agent-mcp-go.service` from an independent unit → check `--version`, `/proc/<MainPID>/exe`, and `/healthz`. TG's `Nix user tools` covers only the upstream tools (agentgateway, skill-validator, skills-manager-cli, tunnel-client-runtime) and neither bumps nor restarts `agent-mcp-go` or `magpie`.
- **The v1.2.4 rollback generation is corrected to `--to 29`.** The old text said v1.2.3 was generation 27. Verified generations: 29 = AMG 1.2.3 + magpie 0.1.4676, 30 = AMG 1.2.4 + magpie 0.1.4692, 31 = AMG 1.2.4 + magpie 0.1.4676. Because the profile also carries magpie, a rollback must name the generation explicitly: stepping back one generation from 31 would keep AMG at 1.2.4 and change only magpie, which reads as a successful rollback while being the wrong outcome.
- Version number is `1.2.5`.

### Live acceptance of the four v1.2.4 fixes

Run against this deployment while it served AMG 1.2.4, 40 tools listed, `annotations_mode=trusted`:

| Fix | Result |
|---|---|
| `grep` accepts a single regular file path | `grep {"path":"/home/agent/code/agent-mcp-go/go.mod","pattern":"module"}` returned `…/go.mod:1:module github.com/bsbofmusic/agent-mcp-go` in the usual `path:line:content` form, where 1.2.3 rejected the path shape |
| `skills_list` sends one compact summary | full catalogue: 53,344 bytes of text against 187,612 bytes of `structuredContent`, i.e. the payload is no longer serialized into the text block |
| `recall` honours `key` / `prefix` | `{"scope":"amg-v125-acceptance","key":"missing"}` returned `{}`; the filter is accepted instead of rejected by the schema |
| empty `skills_root` reads as optional | **not exercised on this deployment** — `skills_root` is set here. Covered by the unit tests only; a deployment that leaves it empty is where the wording is observable |

One observation from that pass, unrelated to the fixes: `grep` with a single path that is a symlink (`/etc/hostname` → `/etc/static/hostname`) is refused with `path escapes from parent`. That is the intended no-symlink rule for a selected path, consistent with the existing directory-walk behaviour, not a regression.

## Compatibility

- No breaking changes. The 40 tool names, descriptions, `inputSchema` values, annotations, and tool count are untouched. `annotations_mode`, the `session_id` type, configuration defaults, settings keys, and ranges are untouched.
- `--version` is additive. A caller that previously relied on `--version` failing with exit 2 gets a version line and exit 0 instead; nothing in the server startup path changed, and `-config` behaviour is identical.
- An older binary still rejects `--version` with exit 2. That is the signal that a rollback to a pre-1.2.5 binary has taken effect.
- The MCP protocol version, `/mcp/stateless` semantics, the OAuth flow, and the `<state_dir>/oauth/state.json` format are unchanged.
- No configuration change is required.

## Installation and verification

Linux amd64. Building from source requires Go 1.25+. Download the archive and checksums from [v1.2.5](https://github.com/bsbofmusic/agent-mcp-go/releases/tag/v1.2.5), follow the [README](https://github.com/bsbofmusic/agent-mcp-go/blob/v1.2.5/README.md), and preserve your configuration and credentials.

```sh
umask 077
CGO_ENABLED=0 go test -count=1 ./...
CGO_ENABLED=0 go vet ./...
CGO_ENABLED=0 go build -buildvcs=false -trimpath -o agent-mcp-go .
```

## Verification

From a source checkout of this tag:

```sh
CGO_ENABLED=0 go test -count=1 -run 'TestVersionStringMatchesConstant' -v .
```

Build and probe the binary directly. This needs no config file and no running service:

```sh
CGO_ENABLED=0 go build -o /tmp/amg-vercheck .
/tmp/amg-vercheck --version    # agent-mcp-go 1.2.5, exit 0
/tmp/amg-vercheck -version     # same line, exit 0
rm -f /tmp/amg-vercheck
```

Against a running deployment, compare the two version probes. Read the token from its file and never print it:

```sh
agent-mcp-go --version
readlink -f "$(command -v agent-mcp-go)"
PID=$(systemctl --user show -p MainPID --value agent-mcp-go.service)
readlink "/proc/$PID/exe"      # must not end in " (deleted)"
curl -fsS http://127.0.0.1:3100/healthz    # ok
TOKEN=$(cat "${AGENT_MCP_GO_TOKEN_FILE:-$HOME/.config/agent-mcp-go/mcp-token}")
curl -s -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"version-check","version":"0"}}}' \
  http://127.0.0.1:3100/mcp | grep -o '"serverInfo":{[^}]*}'
```

`--version` and `serverInfo.version` must both read `1.2.5`, and `/proc/<MainPID>/exe` must resolve to the store path that `command -v agent-mcp-go` resolves to. If `--version` says 1.2.5 while `serverInfo` still says 1.2.4, the service has not been restarted.

## Rollback

Roll back the deployment, not only the process. A Nix profile switch is part of a binary upgrade, so the layers must move together.

1. Name the target generation and restart from an independent unit. This host runs AMG from the `agent-cli` profile, which also carries `magpie`, so the generation number must be explicit — never "the previous generation", because an intermediate generation can correspond to the same AMG version with a different magpie version.

   As of writing, generation **31** is the deployed state this release upgrades away from: **AMG 1.2.4 + magpie 0.1.4676**. Deploying 1.2.5 adds a generation on top of it. **Verify the actual number after deploying** — the new generation had not been created when this note was written, so its number is deliberately not stated here:

   ```sh
   nix profile history --profile /home/agent/.local/state/nix/profiles/agent-cli
   for g in 29 30 31 32; do
     d=/home/agent/.local/state/nix/profiles/agent-cli-$g-link
     [ -e "$d" ] || continue
     printf 'gen %s: ' "$g"
     readlink -f "$d/bin/agent-mcp-go"
     readlink -f "$d/bin/magpie"
   done
   ```

   Pick the generation whose `agent-mcp-go` path is the 1.2.4 store path and whose magpie is the one you intend to run. In the example below the target is **31**, the verified pre-1.2.5 generation; substitute the number you read from `history` if it differs. The agent runtime cannot restart its own control plane, so start the rollback from a separate `systemd-run --user` unit or an SSH session:

   ```sh
   systemd-run --user --unit=amg-rollback --wait --collect \
     nix profile rollback --profile /home/agent/.local/state/nix/profiles/agent-cli --to 31
   systemctl --user restart agent-mcp-go.service
   ```

   The transient unit runs with the user manager's environment; use an absolute `nix` path such as `~/.nix-profile/bin/nix` if the manager's `PATH` does not include it. After the restart, verify the running binary instead of only the profile: `--version` fails with flag exit 2 (the rolled-back binary predates the probe), `serverInfo.version` must be `1.2.4`, `/proc/<MainPID>/exe` must not end in ` (deleted)`, and `/healthz` must answer before the rollback is considered complete:

   ```sh
   agent-mcp-go --version                     # exit 2: expected on 1.2.4
   PID=$(systemctl --user show -p MainPID --value agent-mcp-go.service)
   readlink "/proc/$PID/exe"                  # no " (deleted)" suffix
   curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3100/healthz
   TOKEN=$(cat "${AGENT_MCP_GO_TOKEN_FILE:-$HOME/.config/agent-mcp-go/mcp-token}")
   curl -s -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"rollback-check","version":"0"}}}' \
     http://127.0.0.1:3100/mcp | grep -o '"version":"1\.2\.4"'
   ```

2. Revert the deployment pin. Set `/home/agent/code/host-infra/packages/agent-mcp-go.nix` back to `version = "1.2.4"` with its published hash `sha256-coaLJQJfiUY7/YLZCD4S9WxoUprLQPEHSYhxM58Nxmc=` and commit it. This pin is a manual edit: `tg --maintenance` does not bump `agent-mcp-go`, so nothing silently undoes the rollback, and nothing performs the upgrade on your behalf either.

3. No live setting needs restoring. This release adds no configuration key and changes no default, range, or settings behaviour, so a 1.2.4 binary reads the same configuration unchanged.

No memory keys are involved in this release.

See the [configuration reference](../configuration.md) and the [comparison with v1.2.4](https://github.com/bsbofmusic/agent-mcp-go/compare/v1.2.4...v1.2.5).
